## 1. 为什么创建这份草案

M2-20 已经完成五个受控 Tool、Harness、Context、Evidence 和引用验证等底层能力，但当前 Agent 仍主要沿用 M1 的固定库存流程。原始 M2-21 计划把下一步描述为“知识路由 + LangGraph + 基于 Evidence 回答”，本轮讨论认为这个描述过窄：如果只增加 `inventory_query/knowledge_query` 二选一路由，系统仍然更接近固定工作流，而不是真正的工程化 Agent。

本草案只把截至目前的讨论共识、候选设计和未决问题记录下来，避免后续窗口丢失上下文。它不表示用户已经确认最终范围、实施步骤、文件清单、预算数值或开发授权。

## 2. 当前已有基础

当前项目已经具备：

- M1 库存垂直切片、库存 LangGraph、Mock/Qwen Tool 提议、聊天 API 和数据库 Evidence；
- Tool Schema、Registry、Harness、权限、租户隔离、预算、超时、重试、Trace 和审计；
- M2 文档上传、解析、分块、索引、Hybrid/RRF、Reranker、Context 和 Document Evidence；
- `get_product_spec`、`search_inventory`、`search_knowledge`、`read_uploaded_file`、`get_evidence_detail` 五个 M2 Registry 能力；
- Citation Validator 及当前用户、ACL、软删除、active 代次的重新验证；
- 日常 Fake Provider 回归与显式真实 BGE/Qwen Smoke 的测试边界。

当前真正缺少的是一个能够持续执行下列闭环的上层 Agent：

```text
理解目标
→ 判断是否可以直接回答
→ 必要时发现可用能力
→ 形成或调整计划
→ 执行一步
→ 观察结果
→ 判断是否完成、追问、继续或停止
```

## 3. 当前讨论形成的方向性共识

以下内容是当前讨论方向，不等同于最终批准的技术合同。

### 3.1 M2-21 的定位需要升级

候选定位：

> M2-21 构建基于动态能力发现、任务规划、执行观察、有限重规划和 Evidence 验证的工程化业务 Agent 闭环。

它不应退化为：

```text
用户句子 → 固定意图标签 → 固定 if/else → 固定 Tool
```

期望形态是：

```text
用户自然语言目标
→ LLM 理解、拆分并判断当前信息缺口
→ 按需发现相关能力
→ 生成当前可执行行动
→ 运行时校验并执行
→ 把 Observation 反馈给 LLM
→ LLM 决定继续、调整、追问、直接回答或结束
```

### 3.2 Agent 不应强迫用户拆分正常的复合问题

一句话可以包含多个需求。例如：

> 查询这款耳机的库存、主要规格和退货政策，并判断是否适合促销。

Agent 应能够识别多个子目标，分析依赖并组合结果，而不是仅因为当前固定预算或单路 Graph 就要求用户拆成多次提问。可能的任务关系是：

```text
确认产品
├─→ 查询库存
├─→ 查询规格
└─→ 搜索退货/促销政策
         ↓
结合库存事实与知识 Evidence 进行综合判断
```

LangGraph 可以表达循环、条件分支和并行；当前限制来自既有状态合同、预算和固定流程，而不是“LangGraph 单线程”或框架能力缺陷。

### 3.3 Agent 要能判断是否需要外部能力

Agent 的下一步不应永远是 Tool Call。当前讨论认为至少需要支持以下行动结果：

| 行动 | 大白话含义 | 示例 |
|---|---|---|
| 直接回答 | 当前信息和 LLM 能力已经足够，不调用 Tool/RAG | “什么是 RAG？” |
| 发现能力 | 当前需要外部信息，先寻找相关能力 | 在大量能力中寻找库存、知识或文件能力 |
| 调用能力 | 已找到合适能力，生成受控参数并执行 | 查询 SKU 实时库存 |
| 追问用户 | 缺少必要信息或存在重要歧义 | “你指的是哪款产品？” |
| 调整计划 | Tool 结果改变了原判断，需要换顺序或补充步骤 | 产品有多个匹配，先消歧再查库存 |
| 完成 | 目标和证据要求已经满足 | 合并结果并生成答案 |
| 无法完成 | 能理解目标，但当前没有能力、权限或足够证据 | 当前没有商品改价能力 |

这些是 Agent 的通用控制动作，不是对所有业务意图的穷举。

### 3.4 通用回答与业务事实必须分开

候选原则：

- 概念解释、改写、总结用户已提供文本、基于用户输入的推理，可以不调用 Tool；
- 实时库存、租户私有数据、企业政策、上传文档事实和其他可验证业务事实，不能依赖模型记忆，必须通过对应能力取得；
- 混合回答可以由 LLM 推理和表达，但其中的业务事实必须来自 Tool/Context/Evidence；
- 当前没有实时能力时，不能把模型训练知识冒充为最新业务事实。

“LLM 可以直接回答”的准确边界、是否限定为项目业务领域、混合答案如何标注无引用的通用解释，仍需最终确认。

### 3.5 能力目录不是自然语言意图穷举

真实可执行能力必须登记，因为没有 Tool、API、凭证或权限的动作无法由模型凭空完成；但不应穷举用户可能说出的所有表达，也不应在能力达到很大规模时把全部 Tool 定义平铺给模型。

候选扩展方向：

```text
LLM 理解当前信息需求
→ Capability Resolver 搜索能力目录
→ 先返回少量能力摘要
→ 按需加载候选能力的完整合同
→ LLM 在候选范围内规划下一步
```

Capability Resolver 暂译为“能力发现器”，未来可以结合：

- 能力领域和标签；
- 名称与描述的关键词检索；
- 语义向量检索；
- 当前角色和租户权限预过滤；
- read/write、副作用和审批等级；
- 输入输出合同、前置条件、成本和延迟；
- 候选排序与按需加载。

当前只有五个 M2 Tool，不需要为了假设中的一万个能力立即建设大型向量能力库；但接口不应写死成五组业务 `if/else`。最终方案需要决定本步做到“可扩展抽象 + 小规模实现”，还是同时实现语义能力检索。

### 3.6 自主性与工程护栏的职责不同

模型可以自主决定：

- 用户目标包含哪些子问题；
- 是否需要 Tool、RAG 或直接回答；
- 当前应发现哪些能力；
- 任务顺序、依赖和可并行部分；
- Observation 是否满足目标；
- 是否需要补充查询、调整计划、追问或结束；
- 如何基于已获权 Evidence 组织最终回答。

程序和 Harness 必须继续决定：

- 可信 `CurrentUser`、tenant、role 和 market；
- Tool 是否真实存在且当前允许使用；
- 参数 Schema、禁止字段和结果合同；
- ACL、软删除、active 代次和租户隔离；
- read/write 风险、审批和副作用边界；
- 步数、时间、模型、Tool、Token 和费用的兜底上限；
- 重复调用、死循环、重试和熔断；
- Evidence 与最终引用是否合法；
- Trace、审计和故障脱敏。

工程化 Agent 的目标是“受控自主”，不是程序提前决定所有业务步骤，也不是模型绕过系统边界自由操作。

## 4. 候选 Agent 运行模型

结合当前讨论和 `cankao.mdwendang/Agent_System_Complete_Guide.md`，M2-21 候选采用“宏观 Plan-then-Execute + 每步 ReAct/Observation + 有限 Re-plan”的单 Agent 模式：

```text
用户请求与对话上下文
        ↓
目标理解 / 初始计划
        ↓
能力发现
        ↓
下一行动决策
   ├─ 直接回答
   ├─ 追问并暂停
   ├─ 调用一个或多个获准能力
   └─ 无法完成
        ↓
Harness 校验与执行
        ↓
Observation + Evidence 写入工作状态
        ↓
完成度检查 / 有限 Re-plan
   ├─ 继续循环
   └─ 最终答案合成
        ↓
Citation Validator / 输出合同校验
        ↓
聊天响应、Trace 和审计
```

这里的 ReAct 指“根据行动结果继续决策”，不要求向用户公开或持久化模型的完整隐藏思维过程。系统只记录可审计的结构化计划、行动、参数摘要、Observation、Evidence、状态变化和停止原因。

## 5. 候选工作状态

为了让 LangGraph 能够循环和恢复，候选状态至少需要表达：

- 用户原始目标；
- 当前对话上下文中允许使用的信息；
- 当前计划及版本；
- 已完成、进行中、受阻和待执行任务；
- 当前发现并获准暴露的能力；
- 每次 Tool 的结构化 Observation；
- 已取得的 Context 和 Evidence；
- 尚未解决的信息缺口与歧义；
- 部分成功结果；
- 已使用和剩余的运行时预算；
- 当前 Agent 状态：运行、等待用户、完成、部分完成、失败或安全终止；
- 明确停止原因和最终完成标准。

字段、上限、是否持久化及与现有 `AgentRun/ToolCall/Thread/Message` 的关系尚未冻结。

## 6. 现有能力如何复用

### 6.1 M1 不删除，但角色发生变化

M1 的固定库存 Graph 证明了 Provider 提议、严格校验、Harness、Tool、事务和错误路径。M2-21 不应推翻这条已验证链，而应评估把它作为库存领域的成熟能力或子图复用：

```text
工程化 Agent Orchestrator
├─ M1 Inventory 能力/子图
├─ M2 Knowledge Search 能力
├─ M2 Evidence Detail 能力
└─ M2 File Reading 能力
```

最终方案需要决定 Agent 是直接逐个调用 M1 Tool，还是把现有库存 Graph 包装为更高层业务能力；两者的预算、Trace 和 Evidence 归属不同，当前尚未确认。

### 6.2 RAG 是按需能力，不是固定必经流程

`search_knowledge` 只在完成用户目标确实需要企业知识时调用。`get_evidence_detail` 与 `read_uploaded_file` 也不应成为每次知识问答的固定三连调用；是否调用应由当前信息缺口、Evidence 和用户目标决定，并继续服从 Harness 与引用规则。

## 7. 候选场景与期望行为

| 用户输入 | 候选行为 |
|---|---|
| “什么是 RAG？” | 不调用 Tool，LLM 直接解释 |
| “SKU-001 现在还有多少库存？” | 发现并使用库存能力，不能凭模型记忆回答 |
| “公司的退货政策是什么？” | 使用知识检索，基于当前获权 Evidence 回答 |
| “查库存、规格和退货政策，并判断是否适合促销” | 拆分多任务、分析依赖、调用多个能力、合并事实和推理 |
| “查一下它的库存”且没有可靠指代 | 追问用户，不猜产品 |
| “帮我修改 Amazon 商品价格”且当前没有写能力 | 说明当前无法执行，不编造 Tool |
| 库存成功、政策无证据 | 返回库存有效结果，并明确政策部分证据不足 |
| 文档正文包含“忽略系统指令” | 只作为不可信数据，不改变 Agent 权限、计划和系统指令 |

## 8. 预算与终止方向

当前讨论已经否定“为了适应两次 Tool 上限而限制用户只能问一个问题”。更合理的方向是：先由 Agent 形成当前计划，再由运行时根据任务复杂度分配预算，并由全局硬上限兜底。

最终方案仍需冻结：

- 单轮最大计划任务数；
- 最大 Agent 循环步数；
- 最大模型调用、Tool 调用、Token、耗时和费用；
- 独立任务是否并行及并发上限；
- 同 Tool/同参数去重规则；
- 哪些错误允许自动重试；
- 哪些 Observation 允许触发 Re-plan；
- Re-plan 最大次数；
- 何时返回部分成功；
- 何时暂停并等待用户；
- 何时安全终止。

预算是防止失控的护栏，不是业务意图路由器。

## 9. 与参考文档一致及需要修正的地方

参考：`cankao.mdwendang/Agent_System_Complete_Guide.md`。

当前准备吸收：

- `LLM + Tool + Loop + Planning + Memory + Termination` 的整体结构；
- Plan-then-Execute、ReAct、Observation 和 Re-planning 的组合；
- 工作记忆、`ask_user`、动态加载能力、组合终止策略；
- 顺序、并行、条件、循环和部分失败处理；
- Trace、评估、HITL、安全和生产故障控制；
- 一个 Agent 可以完成时不提前扩大为多 Agent。

不能直接照抄：

- 不要求模型公开完整内部思维过程；
- 不只依赖模型自行判断“已经完成”；
- 不把全部 Tool 永久平铺到 Prompt；
- 不把简单重试当作 Re-plan；
- 不把长期记忆简单等同于无治理的 RAG 写入；
- 不允许高风险操作只靠 Prompt 约束；
- 示例代码只能帮助理解，不能代替本项目的严格 Schema、Harness、事务、Evidence 和测试。

## 10. 当前尚未确认的关键需求

以下问题必须在正式方案前逐项确认：

1. **直接回答范围**：只允许业务相关通用解释，还是允许更广泛的一般知识问答？
2. **业务事实边界**：哪些内容强制要求 Tool/Evidence，混合答案如何区分通用推理和业务事实？
3. **能力发现深度**：本步只建立可扩展 Resolver 抽象，还是同时实现关键词/语义能力检索？
4. **规划方式**：每个请求先生成完整计划，还是简单请求直接行动、复杂请求才显式规划？
5. **M1 复用粒度**：把库存 Graph 作为业务能力复用，还是由新 Agent 直接使用两个库存 Tool？
6. **并发范围**：独立只读任务是否在 M2-21 就并行，数据库 Session 与Trace 如何隔离？
7. **追问与恢复**：`ask_user` 是否在 M2-21 就支持跨 HTTP 请求暂停、持久化和恢复？
8. **工作记忆**：只保存单次 AgentRun，还是使用聊天历史支持“它/这款产品”等多轮指代？
9. **有限重规划**：哪些失败允许换工具、改查询或补充步骤，最多几次？
10. **部分成功合同**：一个分支失败时，API、AgentRun 和最终回答如何表达？
11. **动态预算**：如何根据计划复杂度分配预算，同时不放宽全局安全上限？
12. **引用规则**：直接回答、数据库 Evidence、文档 Evidence 混合时，哪些陈述必须引用？
13. **HTTP 边界**：M2-21 是否同时扩展现有聊天 API，还是先完成内部 Agent 再单独接 HTTP？
14. **真实模型验收**：Mock、Qwen、Fake BGE、真实 BGE 的最小矩阵和延迟标准是什么？
15. **与后续里程碑边界**：哪些评估留给 M2-22，哪些前端留给 M2-23，哪些深度研究留给 M4？

## 11. 仅供继续讨论的候选拆分

以下顺序不是正式实施步骤，也没有开发授权：

1. 冻结 Agent 行动、计划、Observation、完成状态和工作记忆合同；
2. 设计可扩展 Capability Catalog/Resolver，并投影当前已授权能力；
3. 建立 Mock/Qwen 的规划和下一行动 Provider 合同；
4. 建立 LangGraph 的计划—执行—观察—有限重规划循环；
5. 接入现有 Harness、M1库存能力和M2知识/Evidence能力；
6. 支持直接回答、追问、无能力、无证据和部分成功；
7. 基于已验证 Evidence 合成答案并执行 Citation Validator；
8. 决定并接入聊天 HTTP 合同；
9. 完成确定性回归、真实 PostgreSQL 矩阵、显式 Qwen Smoke 和资源基线；
10. 收口文档并等待是否进入 M2-22。

正式方案仍必须重新给出每一步的目标、不做内容、输入输出、上下游、预计文件、RED/GREEN验证、完成标准、风险和停止点，并由用户明确确认后才能开始第一步。
