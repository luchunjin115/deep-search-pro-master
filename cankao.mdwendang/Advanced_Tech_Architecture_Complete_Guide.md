## 第二章：MCP——万物互联的标准协议

### 2.1 是什么：MCP 的定义与背景（面试重点）

```
MCP = Model Context Protocol（模型上下文协议）

大白话：
MCP 就是 AI 世界的 "USB 接口"。

没有 USB 之前：
├─ 每个设备（打印机、键盘、鼠标）都有自己的专用接口
├─ 买了新设备 → 需要找对应的线和驱动
├─ 非常麻烦

有了 USB 之后：
├─ 所有设备都用同一个接口
├─ 即插即用
├─ 一个接口连接万物

AI 领域的问题（MCP 之前）：
├─ 每个 AI 应用要连接外部系统（数据库、API、文件系统...）
├─ 每个连接都要写自定义代码
├─ 换一个 LLM → 所有集成代码可能要重写
├─ N 个 AI 应用 × M 个外部系统 = N×M 个适配器
└─ 这就是 MCP 要解决的 "M×N 问题"

MCP 的解决方案：
├─ 定义一个标准化协议
├─ AI 应用（Client）只需要实现 MCP 协议
├─ 外部系统（Server）也只需要实现 MCP 协议
├─ N 个 Client + M 个 Server = N+M 个适配（不再是 N×M）
└─ 类似于 USB，一次实现，到处连接
```

### 2.2 MCP 的核心概念

```
MCP 架构中的三个角色：

┌──────────────────────────────────────────────────────┐
│                                                      │
│  Host（宿主）                                         │
│  ═══════════                                         │
│  用户直接交互的 AI 应用                                │
│  例如：Claude Desktop、你的 AI 客服系统                 │
│  负责管理连接和用户交互                                │
│                                                      │
│         │  包含一个或多个                              │
│         ▼                                            │
│  Client（客户端）                                     │
│  ═══════════════                                     │
│  Host 内部的 MCP 客户端模块                            │
│  负责和 MCP Server 通信                               │
│  维护 1:1 的 Server 连接                              │
│                                                      │
│         │  通过 MCP 协议连接                           │
│         ▼                                            │
│  Server（服务端）                                     │
│  ═══════════════                                     │
│  提供特定能力的轻量级服务                               │
│  例如：GitHub Server、数据库 Server、搜索 Server       │
│  每个 Server 暴露 Tools / Resources / Prompts         │
│                                                      │
└──────────────────────────────────────────────────────┘


MCP Server 暴露三种能力：

1. Tools（工具）—— 你在 Step 3 学过的 Function Calling
   ├─ 让 LLM 可以执行操作
   ├─ 例如：search_code、create_issue、run_query
   └─ 和 Tool Use 的区别：MCP 把工具定义标准化了

2. Resources（资源）—— 数据访问
   ├─ 让 LLM 可以读取外部数据
   ├─ 例如：文件内容、数据库表、API 返回数据
   └─ 类似于 RAG 的数据源，但通过标准协议访问

3. Prompts（提示模板）
   ├─ 预定义的 Prompt 模板
   ├─ 帮助用户更好地使用 Server 的能力
   └─ 例如：GitHub Server 提供"审查 PR"的 Prompt 模板
```

### 2.3 为什么 MCP 是趋势（面试重点）

```
MCP 之前（你在 Step 3 学的 Tool Use 方式）：

你的 AI 应用想连 GitHub → 写一套 GitHub 集成代码
你的 AI 应用想连 Slack → 再写一套 Slack 集成代码
你的 AI 应用想连数据库 → 再写一套数据库集成代码
换了一个 LLM → 集成代码可能要改
换了一个框架 → 集成代码可能要重写

MCP 之后：

社区已经有现成的 MCP Server：
├─ GitHub MCP Server（别人写好的）
├─ Slack MCP Server（别人写好的）
├─ PostgreSQL MCP Server（别人写好的）
├─ 还有几百个其他 Server...
└─ 你的应用只需要实现 MCP Client → 自动连接所有 Server

这就像 App Store：
├─ 你不需要自己写每个功能
├─ 需要什么能力 → 装一个 MCP Server
├─ 标准化 → 可复用、可共享
└─ 生态越大 → 可连接的系统越多
```

### 2.4 MCP 的传输机制

```
MCP 支持两种传输方式：

1. Stdio（标准输入输出）
   ├─ Server 作为本地进程运行
   ├─ 通过 stdin/stdout 通信
   ├─ 适合：本地工具、CLI 工具
   ├─ 优点：简单、无需网络
   └─ 例如：文件系统 Server、本地数据库 Server

2. SSE（Server-Sent Events）+ HTTP
   ├─ Server 作为远程 HTTP 服务运行
   ├─ 客户端通过 HTTP 发请求，通过 SSE 接收流式响应
   ├─ 适合：远程服务、云端工具
   ├─ 优点：可以远程访问、支持多客户端
   └─ 例如：云端 API Server、SaaS 集成

选哪个：
├─ 本地开发/个人工具 → Stdio（简单直接）
├─ 团队共享/生产部署 → SSE（支持远程和多用户）
```

### 2.5 MCP 对你的影响

```
作为 AI 应用工程师，MCP 意味着：

1. 集成成本大幅降低
   ├─ 以前：每个系统写一套集成代码
   ├─ 现在：直接用现成的 MCP Server
   └─ 节省 50-80% 的集成开发时间

2. 你需要学会的新技能
   ├─ 如何选择和配置 MCP Server
   ├─ 如何开发自定义 MCP Server（当没有现成的时候）
   ├─ 如何在你的应用中集成 MCP Client
   └─ 如何管理多个 MCP Server 的协调

3. 对之前知识的影响
   ├─ Tool Use（Step 3）：MCP 是 Tool Use 的标准化和升级
   ├─ Agent（Step 4）：Agent 通过 MCP 获得更多工具
   ├─ RAG（Step 2）：知识库可以作为 MCP Resource 暴露
   └─ 工程化（Step 5）：MCP Server 的部署和监控

当前状态（2026 年中）：
├─ Anthropic 主导，Claude 深度集成
├─ 越来越多公司支持（OpenAI、Google 等也在跟进）
├─ 社区生态快速增长（数百个 MCP Server）
├─ 已经是面试热门话题
└─ 建议：了解原理 + 会用现成 Server + 能写简单自定义 Server
```

## 第三章：Computer Use——让 AI 操控电脑

### 3.1 是什么：AI 直接操作图形界面

```
大白话：
以前 AI 只能通过 API 和代码和系统交互。
Computer Use 让 AI 能像人一样操作电脑：
├─ 看屏幕截图（理解当前界面）
├─ 移动鼠标（点击按钮、选择菜单）
├─ 敲键盘（输入文字、快捷键）
└─ 完成复杂的 GUI 操作

就像给 AI 装了"眼睛"和"手"：
├─ 眼睛：截图 + 视觉理解 → 知道屏幕上有什么
├─ 手：鼠标 + 键盘控制 → 能操作界面元素
└─ 大脑：LLM 的推理能力 → 知道该做什么操作

和 Tool Use 的区别：
├─ Tool Use：AI 调用 API → 需要系统有 API
├─ Computer Use：AI 操作 GUI → 不需要系统有 API
├─ 很多老旧系统只有 GUI 没有 API
└─ Computer Use 是 Tool Use 的终极补充
```

### 3.2 工作原理

```
Computer Use 的运行循环：

┌─────────────────────────────────────────┐
│                                         │
│  Step 1：截取屏幕截图                    │
│     ↓                                   │
│  Step 2：把截图发给 LLM                  │
│     ↓                                   │
│  Step 3：LLM 分析截图，决定下一步操作     │
│     例如："我需要点击左上角的搜索框"       │
│     ↓                                   │
│  Step 4：执行操作（移动鼠标、点击、输入）  │
│     ↓                                   │
│  Step 5：再次截图，看操作结果             │
│     ↓                                   │
│  回到 Step 2，继续下一步...              │
│                                         │
└─────────────────────────────────────────┘

本质上就是一个 Agent 循环（Step 4 学过的）：
├─ 观察（截图）→ 思考（LLM推理）→ 行动（鼠标键盘）
├─ 和 ReAct 模式完全一致
└─ 只不过"工具"变成了鼠标和键盘

三个核心工具：
├─ computer：截图、鼠标移动、鼠标点击、键盘输入、滚动
├─ text_editor：查看和编辑文件
└─ bash：执行终端命令
```

### 3.3 应用场景

```
场景 1：自动化测试（最成熟的应用）
├─ 传统 UI 测试：写 Selenium 脚本，维护成本高
├─ Computer Use 测试：告诉 AI "注册一个新账号并下单"
├─ AI 像人一样操作界面，自动验证流程
├─ 界面改了也不需要改测试脚本（AI 能自适应）

场景 2：RPA（机器人流程自动化）
├─ 传统 RPA：需要精确配置每一步操作坐标
├─ Computer Use RPA：描述任务目标即可
├─ "把这个 Excel 里的数据填到 SAP 系统中"
├─ 特别适合没有 API 的老旧系统

场景 3：技术支持与远程协助
├─ AI 可以"看到"用户的屏幕
├─ 指导用户操作或直接帮用户操作
├─ "帮我设置一下 VPN 连接"

场景 4：数据采集
├─ 从没有 API 的网站提取数据
├─ 比传统爬虫更灵活（能处理 JS 渲染、验证码等）
└─ 但速度比 API 慢很多
```

### 3.4 局限和注意事项

```
当前局限（务必了解）：

1. 速度慢
   ├─ 每步都要截图 → 发给 LLM → 等推理 → 执行
   ├─ 一步操作可能需要 3-5 秒
   ├─ 复杂流程可能需要几分钟
   └─ 不适合需要实时响应的场景

2. 准确性不够高
   ├─ 点击位置可能有偏差
   ├─ 小按钮、密集界面容易点错
   ├─ 需要"验证 + 重试"机制
   └─ 当前成功率大约 70-90%（视任务复杂度）

3. 成本高
   ├─ 每步都消耗大量 Token（截图很大）
   ├─ 一个复杂任务可能消耗数万 Token
   └─ 如果有 API → 用 API，成本低 100 倍

4. 安全风险
   ├─ AI 能操作你的电脑 → 必须有严格的权限控制
   ├─ 必须在沙箱/虚拟机中运行
   ├─ 不能给 AI 访问敏感系统的权限
   └─ 生产环境中需要 Human-in-the-Loop

什么时候用 Computer Use：
✅ 目标系统没有 API
✅ 操作流程复杂但不要求实时
✅ 自动化测试和验证
✅ 一次性的批量操作

什么时候不用：
❌ 有 API 的系统（直接用 Tool Use）
❌ 需要高速响应的场景
❌ 需要 100% 准确率的关键操作
❌ 涉及支付、删除等高风险操作（除非有人审批）
```

## 第四章：长上下文技术——百万 Token 时代

### 4.1 是什么：上下文窗口的进化

```
大白话：
LLM 的"上下文窗口"就是它一次能看多少内容。

上下文窗口的进化：
├─ GPT-3（2020）：4K tokens ≈ 3000 字
├─ GPT-4（2023）：128K tokens ≈ 10万字
├─ Claude 3.5（2024）：200K tokens ≈ 15万字
├─ Gemini 1.5（2024）：1M tokens ≈ 75万字
├─ Claude（2025+）：持续增长中
└─ 趋势：上下文窗口在快速增大

这意味着什么？
├─ 以前：一次只能"看"几页文档 → 需要 RAG 分块检索
├─ 现在：一次能"看"整本书 → 直接把文档全塞进去？
└─ 核心问题：长上下文 vs RAG，该用哪个？
```

### 4.2 长上下文 vs RAG——最重要的架构决策之一（面试重点）

```
这是面试最容易问到的问题之一：
"有了长上下文，还需要 RAG 吗？"

答案：需要，但使用方式在变化。

长上下文的优势：
├─ 简单：直接把文档塞进 Prompt，不需要分块、embedding、检索
├─ 完整：LLM 能看到完整上下文，不会遗漏
├─ 理解跨段关系：能理解文档前后的关联
└─ 开发快：不需要搭建 RAG 管线

长上下文的劣势：
├─ 成本高：100K tokens 的输入 ≈ 几元人民币/次
├─ 速度慢：输入越长，首 Token 延迟越高
├─ "大海捞针"问题：文档太长时，中间部分容易被忽略
├─ 知识库更新不方便：每次都要重新发送完整文档
└─ 有上限：再大的窗口也装不下全部企业知识库

RAG 的不可替代性：
├─ 知识库很大（几万到几百万文档）→ 无论窗口多大也装不下
├─ 需要实时更新 → RAG 的索引可以随时更新
├─ 需要精确引用来源 → RAG 天然支持溯源
├─ 成本敏感 → RAG 只检索相关部分，省 Token
└─ 多数据源整合 → RAG 可以从多个来源检索

最佳实践——组合使用：

┌────────────────────────────────────────────────┐
│           长上下文 + RAG 的组合策略              │
├────────────────────────────────────────────────┤
│                                                │
│  方案 1：RAG 检索 + 长上下文理解                 │
│  ├─ 用 RAG 从大知识库中检索 Top-K 文档           │
│  ├─ 利用长上下文把 K 设大（20-50 篇而不是 3-5）  │
│  ├─ LLM 在更多上下文中综合理解                   │
│  └─ 效果：检索精度 × 理解深度 双提升             │
│                                                │
│  方案 2：按知识库大小选择                        │
│  ├─ < 50 页：直接用长上下文（全塞进去）           │
│  ├─ 50-500 页：RAG + 长上下文组合                │
│  ├─ > 500 页：必须用 RAG                        │
│  └─ > 10000 页：RAG + 分层索引                  │
│                                                │
│  方案 3：混合架构                                │
│  ├─ 静态知识（不常变）→ 长上下文 / 微调            │
│  ├─ 动态知识（常更新）→ RAG                      │
│  └─ 实时知识（秒级更新）→ Tool Use 直接查询       │
│                                                │
└────────────────────────────────────────────────┘

面试怎么答：
"长上下文不会替代 RAG，但会改变 RAG 的使用方式。
 知识库小可以直接塞，知识库大必须用 RAG。
 最佳实践是组合使用：RAG 负责'找到相关内容'，
 长上下文负责'充分理解上下文'，各取所长。"
```

### 4.3 长上下文的技术挑战

```
"大海捞针"问题（Lost in the Middle）
═══════════════════════════════════
是什么：当输入很长时，LLM 对中间部分的注意力会下降。
大白话：一本 500 页的书，开头和结尾看得仔细，中间看得马虎。

影响：
├─ 关键信息如果在中间 → 可能被忽略
├─ 上下文越长 → 这个问题越严重

缓解方案：
├─ 把最重要的信息放在开头或结尾
├─ 用明确的标记（如 "【重要】"）突出关键信息
├─ 结合 RAG：先检索出最相关的内容 → 放在 Prompt 的头部
└─ 分段处理：先用 LLM 对长文档做摘要 → 再基于摘要回答


成本问题
═══════
├─ 长上下文 = 大量输入 Token = 贵
├─ 100K tokens 输入一次 ≈ 几元人民币
├─ 如果每次请求都塞 100K → 成本爆炸
├─ Prompt Caching（Step 5 学过）可以大幅降低成本
│   第一次请求缓存 → 后续请求复用 → 成本降低 90%
└─ 这就是为什么 Prompt Caching 在长上下文时代特别重要
```

## 第五章：推理模型——会思考的 AI

### 5.1 是什么：Extended Thinking / Chain-of-Thought

```
大白话：
普通 LLM 回答问题是"脱口而出"——看到问题直接给答案。
推理模型是"先想一想再回答"——看到问题先思考一番，再给答案。

就像考试：
├─ 普通学生：看到题目直接写答案
├─ 学霸：看到题目先在草稿纸上推导，再写答案
└─ 推理模型就是那个"用草稿纸"的学霸

技术实现：
├─ Claude 的 Extended Thinking：模型在回答前会先生成
│   一段"思考过程"（thinking tokens），但不展示给用户
├─ OpenAI 的 o1/o3：专门训练的推理模型
├─ 本质：模型在输出答案之前，先用更多 Token 来"推理"
└─ 用更多的计算换更高的准确率
```

### 5.2 为什么用：推理模型解决什么问题

```
推理模型特别擅长的场景：

1. 复杂数学和逻辑推理
   ├─ 普通模型容易在多步推理中出错
   ├─ 推理模型会一步一步验证
   └─ 准确率提升非常显著

2. 代码生成（复杂算法）
   ├─ 普通模型写简单代码没问题
   ├─ 复杂算法容易出 bug
   └─ 推理模型会"检查"自己写的代码逻辑

3. 复杂分析和决策
   ├─ 需要权衡多个因素
   ├─ 需要考虑各种边界条件
   └─ 推理模型会更全面地考虑

4. 规划类任务（Agent 相关）
   ├─ 任务分解
   ├─ 步骤排序
   └─ 推理模型能做出更合理的计划

推理模型不适合的场景：
├─ 简单问答（杀鸡用牛刀，浪费 Token）
├─ 翻译、摘要（不需要复杂推理）
├─ 闲聊（不需要"思考"）
└─ 对延迟敏感的实时交互（thinking 需要时间）
```

### 5.3 怎么用：推理预算与成本权衡

```
推理模型的核心权衡：思考越多越准，但越慢越贵。

思考预算（Thinking Budget）：
├─ 你可以控制模型"想多久"
├─ budget 小 → 想得少 → 快但可能不够准
├─ budget 大 → 想得多 → 准但慢且贵
└─ 需要根据任务复杂度调整

Claude Extended Thinking 的使用：
├─ 在 API 调用中设置 thinking 参数
├─ 可以设置 budget_tokens 控制思考量
├─ thinking 内容不计入最终输出
└─ 但会消耗 Token（影响成本）

实际应用中的策略：
┌───────────────────────────────────────────┐
│  任务类型        │ 推理策略                  │
├───────────────────────────────────────────┤
│  简单问答        │ 不用推理模型（Haiku/Sonnet）│
│  一般生成        │ 不用推理模型（Sonnet）     │
│  复杂分析        │ 用推理模型，中等 budget    │
│  数学/代码       │ 用推理模型，较大 budget    │
│  Agent 规划      │ 用推理模型，大 budget      │
│  关键决策        │ 用推理模型，最大 budget    │
└───────────────────────────────────────────┘

成本对比：
├─ 普通 Sonnet 回答一个问题：0.01 元
├─ 推理模型回答同一个问题：0.05-0.50 元（取决于思考量）
├─ 差 5-50 倍
└─ 所以要有选择地使用，不是所有请求都上推理模型
```

### 5.4 推理模型与 Agent 的结合

```
推理模型对 Agent 系统的影响很大：

之前的 Agent（Step 4）：
├─ 用普通模型做规划 → 计划可能不够周全
├─ 遇到复杂任务 → 可能走弯路
└─ 需要更多步骤才能完成 → 成本高

用推理模型增强的 Agent：
├─ 规划更周全 → 一次制定好完整计划
├─ 工具选择更准 → 减少无效调用
├─ 异常处理更好 → 提前考虑到边界情况
└─ 总步数减少 → 反而可能更省成本

最佳实践——分层使用：
├─ 规划阶段：用推理模型（需要深思熟虑）
├─ 执行阶段：用普通模型（按计划执行即可）
├─ 反思/纠错阶段：用推理模型（需要分析问题）
└─ 这种"混合使用"能在质量和成本之间取得平衡
```

## 第六章：多模态应用——不只是文字

### 6.1 是什么：AI 处理多种类型的信息

```
多模态 = 多种信息模态

模态（Modality）就是信息的类型：
├─ 文本（Text）→ 你之前学的所有内容
├─ 图片（Image）→ 照片、截图、图表
├─ 音频（Audio）→ 语音、音乐
├─ 视频（Video）→ 短视频、直播流
└─ 文档（Document）→ PDF、PPT、Excel

以前的 LLM 只能处理文本。
多模态 LLM 能同时理解多种信息。

大白话：
├─ 以前的 AI 只有"耳朵"（听文字）
├─ 现在的 AI 有了"眼睛"（看图片视频）
├─ 有了"嘴巴"（语音对话）
└─ 越来越像一个完整的"人"
```

### 6.2 视觉理解——最成熟的多模态能力

```
Vision（视觉理解）是目前最成熟、最实用的多模态能力。

能做什么：

1. 图片理解和描述
   ├─ 输入一张图片 → AI 能描述图片内容
   ├─ 输入产品图 → AI 能识别产品特征
   └─ 输入场景图 → AI 能分析场景

2. OCR（文字识别）
   ├─ 识别图片中的文字
   ├─ 发票识别、名片识别
   ├─ 手写体识别
   └─ 多语言文字识别

3. 图表理解
   ├─ 看柱状图 → 分析数据趋势
   ├─ 看流程图 → 理解业务流程
   └─ 看表格截图 → 提取表格数据

4. UI/截图分析
   ├─ 分析网页截图的布局
   ├─ 找出 UI 中的问题
   └─ 这就是 Computer Use 的基础

5. 多图对比
   ├─ 对比两张图的差异
   ├─ 比如：对比两版设计稿的改动
   └─ 或者：对比产品不同角度的照片

实际应用场景：
┌──────────────────┬──────────────────────────┐
│ 应用场景          │ 具体做法                  │
├──────────────────┼──────────────────────────┤
│ 发票自动处理      │ 拍发票照片 → AI提取信息    │
│ 商品识别客服      │ 用户拍照 → AI识别商品并回答 │
│ 文档数字化        │ 扫描纸质文档 → AI提取内容   │
│ 质检              │ 产品照片 → AI检测缺陷      │
│ 医疗影像辅助      │ X光/CT → AI辅助诊断        │
└──────────────────┴──────────────────────────┘
```

### 6.3 语音处理——实时对话的基础

```
语音处理分两个方向：

STT（Speech-to-Text，语音转文字）
═══════════════════════════════
├─ 用户说话 → 转成文字 → 发给 LLM
├─ 工具：OpenAI Whisper、Azure Speech、讯飞
├─ 准确率：中文已经非常高（> 95%）
├─ 关键指标：准确率、延迟、方言支持

TTS（Text-to-Speech，文字转语音）
═══════════════════════════════
├─ LLM 回答文字 → 转成语音 → 播放给用户
├─ 工具：ElevenLabs、Azure TTS、Edge TTS
├─ 关键指标：自然度、情感表达、延迟
├─ 最新趋势：声音克隆（用几秒样本模仿音色）

实时语音对话
════════════
├─ 传统方式：STT → LLM → TTS（三步流水线）
│   延迟 = STT延迟 + LLM延迟 + TTS延迟 ≈ 3-5秒
│   体验不够自然
│
├─ 新方式：原生语音模型
│   模型直接处理音频输入 → 直接输出音频
│   延迟大幅降低 → 接近人类对话体验
│   能理解语气、情感、语调
│
└─ 趋势：从"文本中转"到"原生语音"

应用场景：
├─ AI 语音客服（替代传统 IVR）
├─ AI 外呼（营销、通知、回访）
├─ 语音助手（类似 Siri 但更智能）
├─ 会议纪要（实时转录 + 总结）
└─ 语言学习（口语对话练习）
```

### 6.4 多模态 RAG

```
是什么：
传统 RAG 只检索文本。
多模态 RAG 能同时检索文本和图片。

大白话：
├─ 传统 RAG：图书馆里只有文字书
├─ 多模态 RAG：图书馆里有文字书、画册、照片、图纸
└─ 你问问题时，它能从所有类型的资料中找答案

技术实现：

方法 1：图片描述化（简单但有效）
├─ 先用 Vision 模型把图片转成文字描述
├─ 然后按普通文本做 RAG
├─ 优点：简单，不需要新的基础设施
├─ 缺点：文字描述丢失了部分视觉信息

方法 2：多模态 Embedding（更先进）
├─ 用多模态 Embedding 模型（如 CLIP）同时向量化文本和图片
├─ 文本和图片在同一个向量空间中
├─ 用户问文字问题 → 能检索到相关图片
├─ 优点：保留了完整视觉信息
├─ 缺点：需要多模态 Embedding 模型

应用场景：
├─ 电商：用户描述想要的商品 → 检索出匹配的商品图片
├─ 医疗：描述症状 → 检索相关的医学影像和文献
├─ 工业：描述设备问题 → 检索维修手册中的相关图示
└─ 教育：问一个物理问题 → 检索相关的示意图和公式推导
```

## 第八章：架构设计方法论——从需求到方案

### 8.1 架构设计的思维方式

```
大白话：
架构设计就是"拿到一个需求，给出一套靠谱的技术方案"。

初级工程师拿到需求：
├─ "好的，我用 LangChain + GPT 做一个 RAG"
├─ 直接开写代码
└─ 做到一半发现方向错了，推倒重来

架构师拿到需求：
├─ 先问清楚真正的问题是什么
├─ 分析有哪些技术路线
├─ 评估每条路线的优缺点
├─ 给出推荐方案 + 理由
├─ 识别风险和应对方案
└─ 然后才开始写代码

区别在哪？
├─ 不是"能不能做"，而是"怎么做最合适"
├─ 不是"我会什么技术"，而是"这个问题适合什么技术"
└─ 这种思维方式在面试中非常加分
```

### 8.2 架构设计五步法

```
Step 1：需求分析——搞清楚到底要做什么
═══════════════════════════════════════

和业务方沟通时要问清楚的问题：

功能需求：
├─ 系统要解决什么问题？（不是"做一个 AI 客服"，
│   而是"减少人工客服 50% 的工单量"）
├─ 目标用户是谁？使用场景是什么？
├─ 输入是什么？输出是什么？
├─ 有没有特殊的业务规则或限制？
└─ 现在是怎么做的？痛点在哪？

非功能需求：
├─ 并发量：同时有多少用户在用？
├─ 响应时间：用户能接受等多久？（< 3s？< 10s？）
├─ 准确率：能接受多少错误？（99%？90%？80%？）
├─ 可用性：能接受多少停机时间？
├─ 数据量：知识库有多大？会增长多快？
├─ 预算：月度预算多少？能接受的单次成本？
└─ 合规：有没有数据安全/隐私要求？

大白话：
开餐厅之前，先搞清楚：
├─ 给谁吃？（白领午餐 vs 高端宴请）
├─ 预算多少？（大排档 vs 米其林）
├─ 每天多少客人？（50人 vs 5000人）
└─ 有没有特殊要求？（清真？素食？过敏？）


Step 2：技术选型——选什么模型、什么架构
═══════════════════════════════════════

模型选型：
├─ 任务复杂度 → 决定模型能力等级
│   ├─ 简单任务（分类、提取）→ Haiku/小模型
│   ├─ 一般任务（问答、摘要）→ Sonnet
│   └─ 复杂任务（推理、规划）→ Opus/推理模型
│
├─ 输入类型 → 决定是否需要多模态
│   ├─ 纯文本 → 文本模型
│   ├─ 文本+图片 → Vision 模型
│   └─ 语音 → STT + LLM + TTS
│
├─ 部署要求 → 决定用 API 还是自部署
│   ├─ 数据不能出境 → 自部署开源模型
│   ├─ 没有限制 → API 调用（省事）
│   └─ 混合：敏感数据自部署，其他用 API

架构选型：
├─ 需要外部知识？ → RAG
├─ 需要执行操作？ → Tool Use / MCP
├─ 需要多步推理和自主决策？ → Agent
├─ 需要固定流程？ → 工作流编排
├─ 知识库多大？ → 决定 RAG vs 长上下文
└─ 准确率要求多高？ → 决定是否需要微调


Step 3：架构设计——画出系统蓝图
═════════════════════════════

一个完整的架构图应该包含：
├─ 数据流：数据从哪里来、经过哪些处理、到哪里去
├─ 模块划分：系统分几个模块、各自职责是什么
├─ 接口定义：模块之间怎么通信
├─ 存储设计：用什么数据库、存什么数据
├─ 部署方案：部署在哪里、怎么扩缩容
└─ 监控方案：监控什么指标、怎么告警


Step 4：成本估算——不能做完才发现太贵
═══════════════════════════════════

成本估算公式：

月度 API 成本 =
    日均请求数 ×
    每请求平均 Token 数 ×
    单 Token 价格 ×
    30

示例：
├─ 日均 1000 个请求
├─ 每请求平均 3000 Token（输入 2000 + 输出 1000）
├─ 用 Claude Sonnet
│   输入：$3/M tokens，输出：$15/M tokens
├─ 日成本 = 1000 × (2000×3/1M + 1000×15/1M)
│         = 1000 × ($0.006 + $0.015)
│         = $21/天
├─ 月成本 ≈ $630/月 ≈ ¥4500/月
└─ 加上服务器、数据库等 → 总成本约 ¥6000/月

别忘了：
├─ 评估和测试阶段也消耗 Token
├─ 留 20% 缓冲
├─ 考虑流量增长
└─ 规划成本优化手段（Step 5 学过的 8 种策略）


Step 5：风险评估——什么可能出错
═════════════════════════════

常见风险和应对：

┌───────────────────┬──────────────────────────┐
│ 风险              │ 应对方案                  │
├───────────────────┼──────────────────────────┤
│ 模型 API 挂了     │ 备用模型（Model Fallback） │
│ 准确率不达标      │ 人工兜底 + 持续优化        │
│ 成本超预算        │ 成本上限告警 + 降级策略     │
│ 知识库更新不及时  │ 自动化数据管线             │
│ 用户恶意攻击      │ Prompt 注入防护 + 限流     │
│ 数据泄露          │ 脱敏 + 权限隔离            │
│ 响应太慢          │ 流式输出 + 缓存            │
└───────────────────┴──────────────────────────┘
```

## 第十章：架构决策——选什么、为什么选

### 10.1 决策一：RAG vs 长上下文 vs 微调（面试高频）

```
┌────────────────────────────────────────────────────────┐
│             何时选什么？决策矩阵                         │
├───────────────┬───────────┬────────────┬───────────────┤
│ 考虑因素       │ RAG       │ 长上下文    │ 微调          │
├───────────────┼───────────┼────────────┼───────────────┤
│ 知识库大小     │ 任意大小   │ < 50 页     │ 不适用        │
│ 知识更新频率   │ 随时更新   │ 每次都重传   │ 要重新训练    │
│ 需要引用来源   │ ✅ 天然支持 │ ❌ 不方便   │ ❌ 不支持     │
│ 回答风格定制   │ ❌ 有限    │ ❌ 有限     │ ✅ 擅长       │
│ 部署复杂度     │ 中（要建索引）│ 低（直接塞）│ 高（要训练） │
│ 成本           │ 低-中     │ 高（大量输入）│ 训练贵运行省  │
│ 准确性         │ 中-高     │ 中（可能遗漏）│ 高（领域专精）│
│ 适合场景       │ 知识问答   │ 文档分析    │ 风格/格式定制 │
└───────────────┴───────────┴────────────┴───────────────┘

面试简答版：
├─ 有大量知识需要查询 → RAG
├─ 有少量文档要深度分析 → 长上下文
├─ 需要模型学会特定风格/格式/推理方式 → 微调
├─ 可以组合使用：微调 + RAG 是常见的高级方案
└─ 大多数项目用 RAG 就够了，微调是"最后手段"
```

### 10.2 决策二：Agent vs 固定工作流

```
什么时候用 Agent（自主决策）：
├─ 用户需求不确定（不知道会问什么）
├─ 执行路径不固定（不同问题需要不同工具组合）
├─ 需要灵活应对异常
└─ 例如：通用助手、智能客服

什么时候用固定工作流（按步骤执行）：
├─ 流程固定（每次都是同样的步骤）
├─ 需要高可靠性（不能让 AI 自己"发挥"）
├─ 每一步都需要确定性
└─ 例如：发票处理、文档审批、数据清洗

混合方案（实际中最常见）：
├─ 大框架用工作流（确保流程正确）
├─ 某些步骤内用 Agent（灵活处理）
├─ 例如：客服系统
│   工作流：意图分类 → 分发 → 处理 → 回复
│   Agent：在"处理"这一步自主选择工具
└─ 既有确定性，又有灵活性
```

### 10.3 决策三：用 API vs 自部署模型

```
用 API（调云端模型）：
├─ 优点：不需要 GPU、部署简单、模型最新
├─ 缺点：数据出境、依赖第三方、成本随量增长
├─ 适合：大多数项目、数据不敏感、快速验证

自部署开源模型：
├─ 优点：数据不出境、完全可控、大量使用时更便宜
├─ 缺点：需要 GPU（贵）、部署运维复杂、模型能力通常弱于顶级 API
├─ 适合：数据合规严格、调用量巨大、需要深度定制

混合方案：
├─ 敏感数据 → 自部署模型处理
├─ 非敏感数据 → API 调用（用更强的模型）
├─ 例如：先用自部署小模型做脱敏
│   脱敏后的数据再发给 Claude API 做深度分析
└─ 兼顾安全性和能力
```

## 第十一章：Fine-tuning 微调——什么时候才需要

### 11.1 核心认知：微调不是第一选择

```
非常重要的认知（面试必问）：

80% 的 AI 应用项目不需要微调。

Prompt Engineering + RAG + Agent 能解决大部分需求。
微调是"最后手段"，不是"默认选择"。

大白话：
├─ 你做菜觉得不好吃
├─ 第一步：换个菜谱（Prompt Engineering）
├─ 第二步：用更好的食材（RAG 提供更好的上下文）
├─ 第三步：换个厨房设备（换更强的模型）
├─ 第四步：以上都不行，才考虑去厨师培训班（微调）
└─ 很多人一上来就想微调，是因为对前三步不够熟练
```

### 11.2 什么时候才需要微调

```
需要微调的 5 个信号：

信号 1：特定输出格式/风格无法通过 Prompt 实现
├─ 例如：让模型以公司特有的报告模板格式输出
├─ Prompt 示例太多 → Token 消耗太大
├─ 微调后不需要示例 → 模型"学会了"格式
└─ 判断标准：Few-shot 示例超过 5 个还不够稳定 → 考虑微调

信号 2：需要特定领域的推理方式
├─ 例如：法律条文的推理逻辑
├─ 例如：金融风控的评估逻辑
├─ 通用模型不理解行业特有的判断规则
└─ 判断标准：Prompt 无论怎么写准确率都上不去 → 考虑微调

信号 3：需要极低延迟
├─ RAG 需要检索 → 增加延迟
├─ 长 Prompt 需要更多处理时间
├─ 微调小模型 → 不需要 RAG、Prompt 更短 → 更快
└─ 判断标准：延迟要求 < 500ms 且 RAG 满足不了 → 考虑微调

信号 4：需要大幅降低推理成本
├─ 微调后的小模型可以替代大模型 + 长 Prompt
├─ 例如：微调 Haiku 级别模型达到 Sonnet + RAG 的效果
├─ 推理成本降低 10-50 倍
└─ 判断标准：月 API 成本 > ¥5万且有稳定的任务模式 → 考虑微调

信号 5：无法用 Prompt 描述的复杂映射
├─ 例如：特定的情感分析标准（公司自定义的 1-10 分标准）
├─ 例如：特定的分类体系（行业特有的分类逻辑）
├─ 规则太复杂，Prompt 写不清楚
└─ 判断标准：标注数据容易获取 + 规则太复杂 → 考虑微调
```

### 11.3 微调的核心知识点

```
微调方式的对比：

全参数微调（Full Fine-tuning）：
├─ 修改模型所有参数
├─ 效果最好，但需要大量 GPU 和数据
├─ 成本极高（可能需要几十万）
├─ 只有大公司才考虑

LoRA（Low-Rank Adaptation）：
├─ 只训练一小部分新增参数（占总参数 < 1%）
├─ 效果接近全参数微调
├─ 成本低很多（几百到几千元 GPU 费用）
├─ 当前最推荐的微调方式

QLoRA：
├─ LoRA 的进一步优化
├─ 用量化技术减少内存占用
├─ 可以在消费级 GPU（如 RTX 4090）上微调大模型
├─ 性价比最高

API 微调（最简单）：
├─ 通过 OpenAI / Anthropic 的 API 直接微调
├─ 不需要 GPU，不需要自己训练
├─ 只需要准备数据，上传即可
├─ 灵活性有限，但最省事


数据准备（微调成败的关键）：
├─ 数量：通常 100-1000 条高质量数据就够
├─ 质量远比数量重要
│   100 条精心标注的数据 > 10000 条噪声数据
├─ 格式：对话格式（system/user/assistant）
├─ 多样性：覆盖各种场景和边界情况
├─ 一致性：标注标准要统一
└─ 验证集：留出 10-20% 做验证，防止过拟合
```

### 11.4 微调的决策流程图

```
接到一个 AI 任务：
│
├─ 先试 Prompt Engineering
│   ├─ 效果达标 → 不需要微调 ✅
│   └─ 效果不达标 →
│
├─ 再试 RAG
│   ├─ 效果达标 → 不需要微调 ✅
│   └─ 效果不达标 →
│
├─ 再试更强的模型
│   ├─ 效果达标 → 不需要微调 ✅
│   └─ 效果不达标 →
│
├─ 分析是什么类型的问题
│   ├─ 知识不够 → 补充 RAG 知识库 → 不需要微调
│   ├─ 格式/风格问题 → 可能需要微调
│   ├─ 推理方式问题 → 可能需要微调
│   └─ 成本问题 → 可能需要微调
│
├─ 确认需要微调 →
│   ├─ 有 100+ 条高质量标注数据吗？
│   │   ├─ 没有 → 先攒数据
│   │   └─ 有 →
│   ├─ 用 API 微调还是自己训练？
│   │   ├─ 简单任务 → API 微调（OpenAI/Anthropic）
│   │   └─ 需要更多控制 → LoRA/QLoRA 自训练
│   └─ 微调后评估 → 效果达标？
│       ├─ 达标 → 上线 ✅
│       └─ 不达标 → 分析问题，迭代数据和训练参数
```

### 12.3 数据合规要点

```
作为 AI 应用工程师必须了解的合规知识：

1. 数据出境
   ├─ 用海外模型 API（如 Claude、GPT）= 数据出境
   ├─ 中国《数据安全法》对数据出境有严格要求
   ├─ 个人信息和重要数据原则上不能出境
   ├─ 解决方案：
   │   ├─ 用国内模型 API（通义、文心、Deepseek 等）
   │   ├─ 自部署开源模型
   │   └─ 脱敏后再发给海外 API

2. 个人信息保护
   ├─ 收集用户数据需要告知和同意
   ├─ 最小必要原则（只收集必需的）
   ├─ 用户有权要求删除自己的数据
   └─ 对话日志中可能包含个人信息 → 要脱敏存储

3. AI 透明度
   ├─ 告知用户"你在和 AI 对话"（不能伪装成人）
   ├─ AI 生成的内容要标注
   └─ 用户有权要求转人工

4. 行业特殊要求
   ├─ 金融：不能用 AI 做投资建议（需持牌）
   ├─ 医疗：AI 辅助诊断必须有人工复核
   ├─ 教育：AI 生成内容需要审核
   └─ 法律：AI 建议不构成法律意见
```

## 第十三章：常见问题诊断手册

### 13.1 技术选型纠结症

```
问题：面对一个新项目，不知道该选什么技术栈

诊断：大多数纠结来源于"想选最好的"，但其实没有最好，只有最合适。

解决方案——快速决策框架：

1. 问自己三个问题：
   ├─ 数据能不能出境？
   │   ├─ 不能 → 国产模型 API 或自部署开源模型
   │   └─ 能 → Claude / GPT API
   │
   ├─ 知识库有多大？
   │   ├─ < 50 页 → 长上下文直接塞
   │   ├─ 50-5000 页 → RAG
   │   └─ > 5000 页 → RAG + 分层索引
   │
   └─ 需要执行操作还是只回答问题？
       ├─ 只回答 → RAG 就够
       ├─ 简单操作 → RAG + Tool Use
       └─ 复杂多步操作 → Agent

2. 先用最简单的方案跑通，再逐步优化
   ├─ 第一版：Prompt + 最强模型 → 验证可行性
   ├─ 第二版：加 RAG → 提升知识覆盖
   ├─ 第三版：加 Tool Use → 支持操作
   └─ 不要一开始就搭一个超复杂的架构
```

### 13.2 "怎么都做不好"综合症

```
问题：RAG 效果不好，换了模型还是不好，换了 Prompt 也不好

诊断路径：

Step 1：确认是哪个环节的问题
├─ 让 AI 直接回答（不用 RAG）→ 回答好不好？
│   ├─ 好 → 问题在检索环节
│   └─ 不好 → 问题在模型或 Prompt
│
├─ 手动给 AI 正确文档 → 回答好不好？
│   ├─ 好 → 问题在检索（找不到正确文档）
│   └─ 不好 → 问题在生成（有文档也回答不好）

Step 2：针对性解决
├─ 检索问题：
│   ├─ 检查分块是否合理（太大？太小？把关键信息切断了？）
│   ├─ 检查 embedding 模型（中文用 BGE-M3 通常更好）
│   ├─ 加查询改写（用 LLM 重写用户问题）
│   └─ 加 Reranking（结果重排序）
│
├─ 生成问题：
│   ├─ 检查 Prompt 是否清晰
│   ├─ 检查是否明确了"只基于文档回答"
│   ├─ 试试换更强的模型
│   └─ 检查文档本身的质量（垃圾进垃圾出）

Step 3：记住一个原则
└─ 数据质量 > 模型选择 > Prompt 设计 > 架构复杂度
   先确保数据是好的，再折腾其他的
```

### 13.3 成本失控

```
问题：AI 系统上线后，API 费用远超预期

诊断清单：
├─ Token 消耗在哪里？
│   ├─ 系统 Prompt 太长 → 精简或用 Prompt Caching
│   ├─ 检索文档太多 → 减少 top_k 或加 Reranking
│   ├─ 输出太长 → 限制 max_tokens
│   └─ 多轮对话历史太长 → 做对话摘要压缩
│
├─ 请求量超预期？
│   ├─ 有没有被刷量（恶意调用）→ 加限流
│   ├─ 有没有重复请求 → 加缓存
│   └─ 有没有可以合并的请求 → Batch API
│
├─ 模型选贵了？
│   ├─ 简单任务用了 Opus → 降级到 Sonnet 或 Haiku
│   ├─ 意图分类用了大模型 → 换成小模型或规则
│   └─ 你在 Step 5 学过的 8 种成本优化策略都用上了吗？

快速止血方案：
├─ 设日度/月度成本上限 → 超了就自动降级
├─ 对不同用户设不同额度 → VIP 用 Opus，普通用 Haiku
└─ 开启 Prompt Caching → 立刻降低 30-90% 输入成本
```

### 13.4 架构膨胀

```
问题：系统越做越复杂，维护成本越来越高

症状：
├─ 一个简单的问答系统，用了 5 个数据库
├─ 加了 Agent，但 90% 的问题用 RAG 就能解决
├─ 上了微服务，但团队只有 2 个人
├─ 引入了多 Agent，但任务根本不需要

原则：用最简单的方案解决问题

解决方案：
├─ YAGNI 原则（You Aren't Gonna Need It）
│   不需要的功能不做，不需要的复杂度不加
│
├─ 渐进式架构
│   ├─ V1：单体应用 + 一个 LLM 调用
│   ├─ V2：有问题了再加 RAG
│   ├─ V3：有需要了再加 Agent
│   └─ 不要一开始就设计"终极架构"
│
└─ 定期审查
    ├─ 哪些组件实际被使用了？
    ├─ 哪些可以合并或删除？
    └─ 简化 > 优化
```

### 13.5 前沿技术焦虑

```
问题：每天都有新技术出来，学不过来

解决方案：

1. 分清"要学"和"要知道"
   ├─ 要学（会用）：Prompt、RAG、Tool Use、Agent、工程化、评估
   │   → 这些你已经学了
   ├─ 要知道（了解）：MCP、Computer Use、推理模型、多模态
   │   → 知道能做什么、什么时候用
   └─ 要关注（追踪）：最新模型发布、新框架、新论文
       → 看看新闻就行，不用深入

2. 新技术的判断标准
   ├─ 这个技术解决什么问题？
   ├─ 我现在的项目有这个问题吗？
   ├─ 如果没有 → 了解就行，不用深入
   └─ 如果有 → 做个小 demo 验证

3. 永远不变的核心能力
   ├─ 理解需求的能力
   ├─ 架构设计的能力
   ├─ 评估和优化的能力
   ├─ 这些能力不会因为新技术出现而过时
   └─ 新技术只是工具，你的判断力才是核心
```

   ├─ 工具权限：查询自动执行，修改需确认
   ├─ 降级策略：模型不可用时 → 切备用模型 → 全部转人工
   └─ 评估体系：每日跑评估，关注满意度和转人工率

### Q2：RAG vs 长上下文 vs 微调，分别适合什么场景？

```
参考答案：

三者各有适用场景，通常按优先级选择：

RAG：
├─ 适合：知识库大（几百到几万篇文档）
├─ 适合：知识需要频繁更新
├─ 适合：需要引用来源
├─ 优点：成本可控、知识可实时更新
├─ 缺点：检索可能遗漏、需要搭建管线

长上下文：
├─ 适合：少量文档的深度分析（< 50 页）
├─ 适合：需要理解文档全貌
├─ 优点：简单、不会遗漏
├─ 缺点：成本高、超长时注意力下降（大海捞针问题）

微调：
├─ 适合：需要学习特定格式/风格/推理方式
├─ 适合：Prompt 怎么写都达不到要求
├─ 适合：需要用小模型替代大模型降成本
├─ 优点：推理时不需要额外 Token
├─ 缺点：训练成本高、需要标注数据、不易更新

组合使用：
├─ RAG + 长上下文：检索 top-K 更多文档，LLM 综合理解
├─ 微调 + RAG：模型学会领域推理方式，RAG 提供最新知识
└─ 大多数项目从 RAG 开始，效果不够再考虑其他
```

### Q3：什么是 MCP？它解决了什么问题？

```
参考答案：

MCP（Model Context Protocol）是 Anthropic 提出的开放协议，
为 AI 应用连接外部系统提供了标准化接口。

解决的核心问题——M×N 集成难题：
├─ 之前：N 个 AI 应用 × M 个外部系统 = N×M 个适配器
├─ 之后：N 个 Client + M 个 Server = N+M 个适配器
├─ 大白话：类似于 USB 接口统一了设备连接方式

核心概念：
├─ Host：AI 应用（如 Claude Desktop）
├─ Client：Host 内部的 MCP 客户端模块
├─ Server：提供特定能力的服务（如 GitHub Server、DB Server）
├─ Server 暴露三种能力：
│   ├─ Tools（可执行的操作）
│   ├─ Resources（可读取的数据）
│   └─ Prompts（预定义的提示模板）

传输方式：
├─ Stdio：本地进程通信（适合本地工具）
├─ SSE + HTTP：远程通信（适合云端服务）

对开发者的意义：
├─ 集成成本降低（直接用社区现成的 MCP Server）
├─ 可复用性提高（一个 Server 所有 Client 都能用）
├─ 生态效应（越多人参与，可连接的系统越多）
└─ 已经成为 AI 应用集成的行业标准趋势
```

### Q4：如何做 AI 应用的成本优化？

```
参考答案：

成本优化从 8 个维度入手（在 Step 5 学过，这里结合架构视角）：

1. 模型分层（最有效）
   ├─ 简单任务 → 小模型（Haiku），¥0.001/次
   ├─ 一般任务 → 中模型（Sonnet），¥0.01/次
   ├─ 复杂任务 → 大模型（Opus），¥0.1/次
   └─ 用意图分类路由到合适的模型

2. Prompt Caching
   ├─ 系统 Prompt 和 RAG 文档可以缓存
   ├─ 重复部分不重复计费
   └─ 成本降低 30-90%

3. 缓存和去重
   ├─ 相同问题命中缓存 → 不调 LLM
   ├─ 相似问题语义匹配 → 复用之前的回答
   └─ 热门问题预生成答案

4. Token 优化
   ├─ 精简 System Prompt
   ├─ 减少检索文档数量（精准检索比广撒网好）
   ├─ 对话历史压缩（摘要而非全量）
   └─ 限制输出长度

5. Batch API
   ├─ 非实时任务用批量处理
   ├─ 通常有 50% 折扣
   └─ 适合评估、数据处理等

6. 架构层面
   ├─ 简单问题不走 LLM（规则匹配、FAQ 直接返回）
   ├─ 不需要 Agent 就不用 Agent
   └─ 减少不必要的 LLM 调用次数

7. 监控和告警
   ├─ 实时监控 Token 消耗
   ├─ 异常消耗自动告警
   └─ 日度/月度预算上限

8. 成本 = 质量 × 速度的权衡
   ├─ 不是越便宜越好
   ├─ 省下的成本不能以牺牲用户体验为代价
   └─ 用评估体系（Step 6）验证优化后质量没下降
```

### Q5：Agent 系统和普通 RAG 问答的架构有什么区别？

```
参考答案：

核心区别在于"循环"和"工具"。

RAG 问答架构（单次流程）：
用户提问 → 检索文档 → LLM 生成回答 → 返回
├─ 一问一答，没有循环
├─ 没有工具调用
├─ 没有自主决策
├─ 简单、快速、可靠

Agent 架构（循环流程）：
用户提问 → LLM 思考 → 选择工具 → 执行 → 观察结果 →
再思考 → 可能再调工具 → ... → 最终回答
├─ 有循环（可能执行多步）
├─ 有工具调用（查数据库、调 API 等）
├─ 有自主决策（LLM 决定下一步做什么）
├─ 灵活但复杂、慢、可能出错

关键架构差异：

                RAG 问答          Agent 系统
────────────────────────────────────────────
执行步数        固定 1 步          不确定（1-N 步）
工具调用        无                 有（多种工具）
决策主体        固定流程           LLM 自主决策
终止条件        检索+生成完就结束   需要设计终止条件
成本可预测性    高                 低（步数不定）
可靠性          高                 中（可能走偏）
延迟            低（2-5s）         高（5-60s）
适合场景        知识查询           任务执行

架构选择建议：
├─ 先用 RAG 能不能解决 → 能解决就不上 Agent
├─ 需要执行操作才用 Agent
├─ 可以混合：大部分走 RAG，需要操作时切到 Agent
└─ Agent 一定要设最大步数和成本上限
```

### Q6：推理模型（Extended Thinking）什么时候用？

```
参考答案：

推理模型的本质是"用更多计算换更高准确率"。

适合用的场景：
├─ 复杂逻辑推理（多步推理、数学问题）
├─ 复杂代码生成（算法实现、架构设计）
├─ Agent 的规划阶段（任务分解、策略制定）
├─ 关键决策（技术方案评估、风险分析）
└─ 复杂分析（长文档对比、多维度评估）

不适合用的场景：
├─ 简单问答（杀鸡用牛刀）
├─ 翻译、摘要（不需要复杂推理）
├─ 闲聊（不需要"深度思考"）
├─ 延迟敏感的实时交互（thinking 需要额外时间）
└─ 成本敏感的高频调用（thinking tokens 要钱的）

最佳实践——分层使用：
├─ Agent 规划阶段 → 推理模型（需要深思熟虑）
├─ Agent 执行阶段 → 普通模型（按计划执行）
├─ Agent 反思阶段 → 推理模型（需要分析问题）
└─ 这样在质量和成本之间取得平衡
```

### Q7：多模态 AI 应用有哪些实际场景？技术方案怎么选？

```
参考答案：

当前最成熟的多模态应用场景：

1. 文档处理（最成熟）
   ├─ 场景：发票识别、合同审查、表格提取
   ├─ 技术：Vision 模型直接理解文档图片
   ├─ 优于传统 OCR：能理解版面布局和语义
   └─ 选型：Claude Vision / GPT-4V

2. 视觉问答（广泛使用）
   ├─ 场景：用户拍照提问、商品识别、UI 分析
   ├─ 技术：图片 + 文本一起发给 Vision 模型
   └─ 选型：各家大模型的 Vision 能力都可以

3. 语音交互（快速增长）
   ├─ 场景：语音客服、会议纪要、口语学习
   ├─ 传统方案：STT → LLM → TTS（三步流水线）
   ├─ 新方案：原生语音模型（端到端，延迟更低）
   └─ 选型：传统方案用 Whisper + LLM + TTS
           新方案用 GPT-4o realtime 或同级产品

4. 多模态 RAG（正在成熟）
   ├─ 场景：图文混合知识库检索
   ├─ 简单方案：图片 → Vision 模型描述 → 按文本 RAG 处理
   ├─ 高级方案：CLIP embedding 做图文联合检索
   └─ 选型：简单场景先用描述化方案

技术方案选择原则：
├─ 先确认是否真的需要多模态（很多场景纯文本够用）
├─ 优先用最简单的方案（图片描述化 > 多模态 embedding）
├─ 语音场景优先用成熟的 STT/TTS 管线
└─ 关注延迟和成本（多模态 Token 消耗更大）
```

### Q8：如何做一个 AI 项目的技术方案评审？

```
参考答案：

评审一个 AI 技术方案，我会从以下维度检查：

1. 需求对齐
   ├─ 方案解决的是不是真正的问题？
   ├─ 有没有遗漏关键需求？
   └─ 非功能需求（并发、延迟、成本）有没有考虑？

2. 技术选型合理性
   ├─ 为什么选这个模型？对比过其他选项吗？
   ├─ 为什么用 RAG / Agent / 微调？有更简单的方案吗？
   ├─ 框架选择有没有过度设计？
   └─ "用最简单的方案解决问题"原则

3. 成本估算
   ├─ 月度 Token 成本估算过吗？
   ├─ 基础设施成本（服务器、数据库）估算过吗？
   ├─ 有没有成本优化策略？
   └─ 成本和预算匹配吗？

4. 风险识别
   ├─ 模型 API 挂了怎么办？（降级策略）
   ├─ 准确率不达标怎么办？（兜底方案）
   ├─ 成本超了怎么办？（上限保护）
   ├─ 安全问题怎么防？（注入、泄露）
   └─ 合规风险考虑了吗？（数据出境）

5. 评估方案
   ├─ 怎么衡量系统好不好用？
   ├─ 有评估数据集吗？
   ├─ 有自动化评估管线吗？
   ├─ 上线后怎么监控？
   └─ 没有评估方案的技术方案是不完整的

6. 迭代计划
   ├─ 先做什么后做什么？
   ├─ MVP 是什么？多久能上线？
   ├─ 后续优化的方向是什么？
   └─ 有没有过度设计/提前优化的问题？
```

### Q9：如何从零搭建一个企业级 AI 应用？

```
参考答案：

分四个阶段，每个阶段有明确的交付物：

第一阶段：验证可行性（1-2 周）
├─ 用最简单的方式跑通核心流程
├─ Prompt + 最强模型 → 看效果上限
├─ 如果效果上限就不行 → 这个需求可能不适合 AI
├─ 交付物：可行性报告 + Demo

第二阶段：搭建 MVP（2-4 周）
├─ 搭建 RAG / Agent 核心能力
├─ 搭建 API 服务（FastAPI + Docker）
├─ 建立评估数据集（50+ 条）
├─ 基础评估（LLM-as-Judge）
├─ 交付物：可用的 MVP + 评估报告

第三阶段：生产化（2-4 周）
├─ 完善安全防护（Prompt 注入防御、输出过滤）
├─ 搭建监控告警
├─ 成本优化（模型分层、Prompt Caching）
├─ 搭建自动化评估管线
├─ A/B 测试框架
├─ 交付物：可上线的生产系统

第四阶段：持续优化（长期）
├─ 收集用户反馈
├─ Bad Case 分析和修复
├─ 评估集持续扩充
├─ 性能和成本持续优化
├─ 新技术跟踪和引入
├─ 交付物：持续提升的评估指标

关键原则：
├─ 先跑通再优化，不要一开始就追求完美
├─ 用评估数据说话，不凭感觉做决策
├─ 简单方案优先，复杂方案按需引入
└─ 每个阶段有明确的验收标准
```

### Q10：Computer Use 和 Tool Use 的区别是什么？分别什么时候用？

```
参考答案：

本质区别：

Tool Use（你在 Step 3 学的）：
├─ AI 通过调用 API / 函数 来操作系统
├─ 需要目标系统提供 API
├─ 精确、快速、可靠
├─ 成本低（一次 API 调用）

Computer Use：
├─ AI 通过截图 + 鼠标 + 键盘 来操作 GUI
├─ 不需要目标系统提供 API
├─ 准确率较低、速度慢
├─ 成本高（每步都要发截图给 LLM）

选择原则：
├─ 有 API → 一定用 Tool Use（快、准、便宜）
├─ 没 API → 考虑 Computer Use（唯一选择）
├─ Computer Use 是 Tool Use 的补充，不是替代

Computer Use 的最佳场景：
├─ 自动化测试（像人一样操作 UI 验证功能）
├─ 老旧系统 RPA（没有 API 的遗留系统）
├─ 一次性批量操作（不值得为其开发 API）
└─ 跨应用工作流（需要操作多个不同的 GUI 应用）

Computer Use 不适合：
├─ 高频调用场景（太慢太贵）
├─ 需要 100% 可靠的关键操作
├─ 有 API 可用的场景
└─ 实时交互场景
```
