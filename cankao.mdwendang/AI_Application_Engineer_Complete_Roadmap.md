## Step 3：Function Calling & Tool Use

> **一句话概括：** 让 LLM 不只是说，还能做。

### 3.1 为什么紧接着学这个

```
你已经会的：
├─ Prompt → 让 LLM 生成文本
├─ RAG → 让 LLM 基于检索内容生成文本

你还缺的关键能力：
└─ LLM 只能"说"，不能"做"

Function Calling 解决的问题：
├─ 用户说"帮我查一下北京今天的天气" → LLM 调用天气 API
├─ 用户说"帮我订明天上午的会议室" → LLM 调用日历系统
├─ 用户说"帮我查一下这个客户的订单状态" → LLM 查询数据库
└─ 不再只是回答问题，而是帮用户完成任务
```

### 3.2 核心知识点

```
Function Calling 知识结构：

├─ 基础概念
│   ├─ 什么是 Function Calling（LLM 输出结构化的函数调用请求）
│   ├─ 什么是 Tool Use（更通用的叫法，Claude 用这个术语）
│   └─ 调用流程：用户提问 → LLM 决定调用什么函数 → 
│               执行函数 → 把结果返回给 LLM → LLM 生成最终回答
│
├─ 工具定义（Tool Definition）
│   ├─ 工具名称、描述、参数的 JSON Schema 设计
│   ├─ 描述的质量直接决定 LLM 选对工具的概率
│   ├─ 参数校验：必填/选填、类型约束、枚举值
│   └─ 最佳实践：单一职责、命名清晰、错误信息有意义
│
├─ 工具选择与编排
│   ├─ 单工具调用：一个问题调一个工具
│   ├─ 多工具顺序调用：先查库存 → 再下单
│   ├─ 多工具并行调用：同时查天气和查日历
│   └─ 工具选择的 Prompt 设计
│
├─ 安全控制
│   ├─ 只读 vs 写操作的权限分离
│   ├─ 参数注入防御
│   ├─ 调用频率限制
│   └─ 人工确认机制（危险操作前要用户确认）
│
└─ 错误处理
    ├─ 工具调用失败怎么办
    ├─ 参数不合法怎么办
    └─ 让 LLM 看到错误信息并自行调整
```

### 3.3 和前序知识的关系

```
Prompt Engineering 在这里的应用：
├─ 工具描述就是 Prompt 的一种（决定 LLM 如何理解工具）
├─ System Prompt 中需要指导 LLM 何时该用工具、何时不该用
└─ 工具返回结果后，LLM 的回答质量仍然依赖 Prompt 设计

RAG 在这里的应用：
├─ "查知识库"本身就是一个 Tool
├─ RAG 可以作为 Agent 的一个工具
└─ 检索+执行是 Agent 最常见的组合
```

### 3.4 实战方向

| 项目 | 难度 | 工具类型 |
|------|------|----------|
| 天气查询助手 | 入门 | 单个 API 工具 |
| 数据库查询助手（Text-to-SQL） | 中等 | 数据库工具 |
| 邮件/日历管理助手 | 中等 | 多个工具协同 |
| 客服系统（查单 + 退款 + 转人工） | 进阶 | 多工具 + 业务逻辑 |

## Step 4：Agent 系统

> **一句话概括：** 让 LLM 自主思考、规划、执行多步骤任务。

### 4.1 为什么在 Function Calling 之后学

```
Function Calling = LLM 调用一次工具
Agent = LLM 持续调用工具直到任务完成

Agent 是 Prompt + RAG + Tool Use 的集大成者：
├─ 用 Prompt 定义 Agent 的角色和行为
├─ 用 RAG 给 Agent 提供知识
├─ 用 Tool Use 给 Agent 执行能力
└─ 加上循环和规划 → 就是一个 Agent
```

### 4.2 核心知识点

```
Agent 知识结构：

├─ Agent 设计模式
│   ├─ ReAct（Reasoning + Acting）
│   │   └─ 思考 → 行动 → 观察 → 循环
│   ├─ Plan-then-Execute
│   │   └─ 先制定计划 → 逐步执行 → 偏离时重新规划
│   ├─ 分层 Agent（Orchestrator + Sub-Agents）
│   │   └─ 主 Agent 分解任务 → 子 Agent 各司其职
│   └─ 反思型 Agent（Reflexion）
│       └─ 执行 → 自我评价 → 改进 → 重试
│
├─ 记忆系统
│   ├─ 短期记忆：当前对话上下文
│   ├─ 长期记忆：跨会话的持久化存储
│   ├─ 工作记忆：当前任务的中间状态
│   └─ 外部记忆：RAG 知识库
│
├─ 规划能力
│   ├─ 任务分解（把大任务拆成子任务）
│   ├─ 优先级排序
│   ├─ 依赖关系管理
│   └─ 异常处理和重新规划
│
├─ 工具编排
│   ├─ 动态工具选择
│   ├─ 工具链（一个工具的输出是另一个的输入）
│   ├─ 并行工具调用
│   └─ 工具结果的汇总和决策
│
├─ 多 Agent 协作
│   ├─ Agent 间通信
│   ├─ 任务分配
│   ├─ 冲突解决
│   └─ 结果汇总
│
├─ 终止与安全
│   ├─ 终止条件设计（什么时候停下来）
│   ├─ 最大步数限制
│   ├─ 成本预算控制
│   ├─ 危险操作拦截
│   └─ 人工介入机制（Human-in-the-Loop）
│
└─ Agent 框架
    ├─ Claude Agent SDK（Anthropic 官方）
    ├─ LangGraph（LangChain 团队）
    ├─ CrewAI（多 Agent 框架）
    ├─ AutoGen（微软）
    └─ 自建 Agent 循环（最可控）
```

### 4.3 实战方向

| 项目 | 难度 | 核心能力 |
|------|------|----------|
| 自动化研究助手（搜索 + 总结） | 中等 | ReAct + 工具调用 |
| 代码生成 Agent（写代码 + 运行 + 修复） | 中等 | 反思型 Agent |
| 数据分析 Agent（SQL + 图表 + 报告） | 进阶 | 多工具编排 |
| 项目管理 Agent（多 Agent 协作） | 高级 | 多 Agent + 人工审批 |
| 上一次对话的供应商合同审查 Agent | 高级 | 全技术栈综合 |

## Step 5：工程化基础

> **一句话概括：** 把 AI 能力从 Jupyter Notebook 搬到生产环境。

### 5.1 为什么在 Agent 之后学

```
此时你已经能：
├─ 写 Prompt → 生成高质量回答
├─ 建 RAG → 基于知识库问答
├─ 做 Agent → 自主执行多步骤任务

但这些都只是在本地跑通了。要让其他人用起来：
├─ 需要 API 接口 → 后端工程
├─ 需要稳定运行 → 部署运维
├─ 需要处理并发 → 性能工程
├─ 需要控制成本 → 成本优化
└─ 需要可观测 → 监控告警
```

### 5.2 核心知识点

```
工程化知识结构：

├─ API 设计与开发
│   ├─ RESTful API 设计
│   ├─ FastAPI / Flask 框架
│   ├─ 流式输出（SSE / WebSocket）
│   ├─ 认证和授权（API Key / OAuth）
│   └─ 请求限流和降级
│
├─ LLM API 调用最佳实践
│   ├─ 重试策略（指数退避）
│   ├─ 超时处理
│   ├─ 降级策略（主模型不可用时切换备用模型）
│   ├─ 流式输出（Streaming）
│   ├─ Prompt Caching（提示缓存）
│   └─ 批处理（Batch API）
│
├─ 部署
│   ├─ Docker 容器化
│   ├─ 云服务部署（AWS / 阿里云 / 腾讯云）
│   ├─ Serverless 部署
│   └─ 模型服务部署（如果需要自部署模型）
│
├─ 监控与可观测性
│   ├─ 日志设计（结构化日志）
│   ├─ 链路追踪（每次请求的完整路径）
│   ├─ 性能监控（延迟、吞吐量、错误率）

│
└─ 数据管线

## Step 6：评估体系

> **一句话概括：** 用数据证明系统好用，用数据驱动优化。

### 6.1 为什么在工程化之后学

```
此时你的系统已经：
├─ 功能完整
├─ 可以被用户访问
└─ 需要回答一个关键问题："它到底好不好用？"

没有评估体系：
├─ 改了 Prompt 不知道是变好了还是变坏了
├─ 换了模型不知道性价比怎么样
├─ 用户说"不好用"但不知道具体差在哪里
└─ 无法向老板证明项目的价值
```

### 6.2 核心知识点

```
评估体系知识结构：

├─ 评估数据集构建
│   ├─ 标注规范设计
│   ├─ 评估集的规模和覆盖度
│   ├─ 边界案例和对抗样本
│   └─ 持续积累（每个 Bad Case 都加入评估集）
│
├─ 自动化评估
│   ├─ LLM-as-Judge（用 AI 评价 AI）
│   │   ├─ Judge Prompt 设计
│   │   ├─ 去偏技巧（位置交换、匿名化）
│   │   └─ Judge 一致性校准
│   ├─ 参考答案对比（BLEU、ROUGE、BERTScore）
│   ├─ 事实性检测（Faithfulness）
│   └─ 分维度评分（准确性、完整性、格式、安全性）
│
├─ 迭代评估
│   ├─ GSB 评价（Good / Same / Bad）
│   ├─ Elo Rating
│   ├─ 回归测试（改了不能变差）
│   └─ A/B 测试（线上对比）
│
├─ RAG 专项评估
│   ├─ 检索质量（Recall@K, MRR, NDCG）
│   ├─ 生成质量（Faithfulness, Relevancy）
│   ├─ 端到端（Answer Accuracy）
│   └─ RAGAS 框架使用
│
├─ Agent 专项评估
│   ├─ 任务完成率
│   ├─ 步骤效率（用了几步完成）
│   ├─ 工具选择准确率
│   ├─ 成本效率
│   └─ 安全性（有没有执行危险操作）
│
└─ 评估驱动优化
    ├─ Bad Case 分析方法论
    ├─ 根因定位（是检索问题还是生成问题）
    ├─ A/B 测试框架
    └─ 持续集成评估（每次改代码自动跑评估）
```

## Step 7：Fine-tuning 微调

> **一句话概括：** 当 Prompt + RAG 解决不了的问题，用微调来定制模型行为。

### 7.1 什么时候才需要学微调

```
重要认知：微调不是必须的技能！

80% 的 AI 应用项目不需要微调。
Prompt Engineering + RAG + Agent 能解决大部分需求。

需要微调的场景：
├─ 需要模型学会特定的输出格式/风格
│   例：让模型以你公司的报告模板格式输出
├─ 需要模型掌握特定领域的推理方式
│   例：让模型学会你公司特有的合同审查逻辑
├─ 需要极低延迟，不能用 RAG
│   例：用小模型微调替代大模型+RAG
├─ 需要减少 Token 消耗
│   例：微调后的模型不需要那么长的 Prompt
└─ 需要处理 Prompt 无法描述的复杂映射
    例：特定的分类规则、评分逻辑
```

### 7.2 核心知识点

```
Fine-tuning 知识结构：

├─ 基础概念
│   ├─ 全参数微调 vs LoRA vs QLoRA
│   ├─ SFT（监督微调）vs RLHF vs DPO
│   ├─ 训练数据格式和准备
│   └─ 过拟合和泛化
│
├─ 数据准备（最关键的环节）
│   ├─ 训练数据的数量和质量
│   │   ├─ 最少需要多少数据（通常 100-1000 条高质量数据）
│   │   └─ 数据质量 >> 数据数量
│   ├─ 数据格式
│   │   ├─ 对话格式（system/user/assistant）
│   │   └─ 指令格式（instruction/input/output）
│   ├─ 数据清洗和去重
│   └─ 数据增强技术
│
├─ 训练实践
│   ├─ 超参数选择（learning rate、epochs、batch size）
│   ├─ LoRA 参数选择（rank、alpha、target modules）
│   ├─ 训练监控（loss 曲线、过拟合检测）
│   └─ 模型评估和对比
│
├─ 微调平台和工具
│   ├─ 云端：OpenAI Fine-tuning API、Claude Fine-tuning
│   ├─ 开源：Hugging Face Transformers + PEFT
│   ├─ 框架：Axolotl、LLaMA-Factory
│   └─ 平台：Anyscale、Together AI
│
└─ 微调 vs 其他方案的权衡
    ├─ 微调 vs Prompt Engineering
    ├─ 微调 vs RAG
    ├─ 微调 vs 微调+RAG（组合使用）
    └─ 成本分析（训练成本 vs 推理成本节省）
```

### 7.3 实战方向

| 项目 | 难度 | 核心技能 |
|------|------|----------|
| 用 OpenAI API 微调一个分类模型 | 入门 | 数据准备 + API 微调 |
| 用 LoRA 微调一个开源模型做特定任务 | 中等 | LoRA + 训练监控 |
| 微调一个领域专用的小模型替代大模型+RAG | 进阶 | 全链路优化 |

## Step 8：多模态应用

> **一句话概括：** 让 AI 不只处理文本，还能理解图片、音频、视频。

### 8.1 为什么放在后面学

```
多模态是能力的扩展，不是基础：
├─ 前面学的所有技术（Prompt、RAG、Agent）在多模态中都适用
├─ 只是输入从"文本"扩展到了"文本+图片+音频+视频"
├─ 核心思想不变，应用场景更广
└─ 市场需求正在快速增长
```

### 8.2 核心知识点

```
多模态知识结构：

├─ 视觉理解（Vision）
│   ├─ 图片理解和描述
│   ├─ OCR（文字识别）
│   ├─ 图表/表格理解
│   ├─ UI 截图分析
│   ├─ 多图对比分析
│   └─ 视觉 RAG（检索图片内容）
│
├─ 语音处理
│   ├─ STT（Speech-to-Text，语音转文字）
│   │   └─ Whisper、Azure Speech、讯飞
│   ├─ TTS（Text-to-Speech，文字转语音）
│   │   └─ ElevenLabs、Azure TTS、Edge TTS
│   └─ 语音对话系统（实时对话）
│
├─ 视频理解
│   ├─ 视频内容分析
│   ├─ 视频摘要
│   └─ 视频问答
│
├─ 文档理解
│   ├─ 复杂 PDF（含图表、公式）的理解
│   ├─ 发票/收据自动识别
│   ├─ 手写文字识别
│   └─ 多页文档跨页理解
│
└─ 多模态 RAG
    ├─ 图文混合检索
    ├─ 图片向量化（CLIP embedding）

## Step 9：安全与合规

> **一句话概括：** 确保 AI 系统不会被攻击、不会泄露数据、不会违反法规。

### 9.1 为什么必须学

```
AI 应用在企业中落地，安全不是可选项：

├─ Prompt 注入攻击 → 用户绕过你的限制做恶意操作
├─ 数据泄露 → AI 把 A 用户的数据告诉 B 用户
├─ 内容安全 → AI 生成不当内容
├─ 合规要求 → GDPR、数据出境、行业监管
└─ 成本攻击 → 恶意用户大量调用消耗你的 API 额度
```

### 9.2 核心知识点

```
安全与合规知识结构：

├─ Prompt 安全（你在 Step 1 已有基础）
│   ├─ 注入攻击（Direct / Indirect）
│   ├─ 越狱防御
│   ├─ System Prompt 防泄露
│   └─ 多层防御架构
│
├─ 数据安全
│   ├─ PII（个人身份信息）检测和脱敏
│   ├─ 数据隔离（多租户环境）
│   ├─ 传输加密（TLS/mTLS）
│   ├─ 存储加密
│   └─ 日志脱敏
│
├─ 内容安全
│   ├─ 有害内容检测
│   ├─ 输出过滤
│   ├─ 内容审核管线
│   └─ 人工审核机制
│
├─ 合规
│   ├─ 数据出境（使用海外 API 时）
│   ├─ 用户隐私（GDPR、个人信息保护法）
│   ├─ AI 透明度（告知用户在和 AI 对话）
│   ├─ 审计追溯
│   └─ 行业特定合规（金融、医疗、教育）
│
└─ 运营安全
    ├─ API Key 管理
    ├─ 请求限流
    ├─ 异常检测
    ├─ 成本上限保护
    └─ 灾备方案
```
